# Email-digest pipeline — primary-source research

Date: 2026-09-05
Scope: technical facts needed to plan the "forward a newsletter → parse links → auto-create jobs in a Space" pipeline, built on Cloudflare Email Routing + Workers in front of the existing FastAPI backend. Research only — no code changes.

---

## 1. Cloudflare Email Routing → Worker mechanics

### Key Takeaways

- The Worker entry point is a dedicated handler, not `fetch()`: `async email(message, env, ctx)`, where `message` is a `ForwardableEmailMessage`. — [Email Workers](https://developers.cloudflare.com/email-routing/email-workers/)
- `ForwardableEmailMessage` exposes: `from: string` (envelope MAIL FROM), `to: string` (envelope RCPT TO — i.e., the exact address dialed, including any local-part detail), `headers: Headers` (standard `Headers` object), `raw: ReadableStream` (raw MIME byte stream), `rawSize: number`, plus methods `forward(rcptTo, headers?)` (headers limited to `X-*`), `reply(EmailMessage)`, and `setReject(reason)`. — [Email Workers](https://developers.cloudflare.com/email-routing/email-workers/), consolidated reference at [llms-full.txt](https://developers.cloudflare.com/email-routing/llms-full.txt)
- There is no built-in "send to webhook" action — that must be code inside the Worker: read/forward `message.raw` and `POST` it (or a parsed version of it) via `fetch()` to the external HTTPS endpoint from inside the `email()` handler. A minimal pattern: `await fetch('https://api.leondev.xyz/...', { method: 'POST', body: message.raw, headers: {...} })` or parse first (see next bullet) and send JSON.
- To actually decode the MIME body (subject/text/html/attachments) inside the Worker, the community-standard tool is **postal-mime** (npm `postal-mime`), which has an explicit Cloudflare Workers guide: `import PostalMime from 'postal-mime'; const email = await PostalMime.parse(message.raw);` — it accepts the `ReadableStream` directly (no manual buffering needed), and exposes `.from`, `.subject`, `.text`, `.html`, `.attachments`. The guide recommends configurable limits (`maxNestingDepth`, `maxHeadersSize`) and says malformed emails are common enough that parse errors must always be handled. — [postal-mime Cloudflare Workers guide](https://postal-mime.postalsys.com/docs/guides/cloudflare-workers/)
- **Size cap**: inbound messages over **25 MiB** are rejected outright by Email Routing before the Worker ever runs. — [Email Routing Limits](https://developers.cloudflare.com/email-routing/limits/), confirmed in [llms-full.txt](https://developers.cloudflare.com/email-routing/llms-full.txt) ("Email Routing does not support messages bigger than 25 MiB")
- **Free at low volume**: Email Routing itself is stated to be "free and private by design" with no separate pricing tier — cost only enters via Workers plan limits. On the **Workers Free plan**, an `email()` handler that exceeds CPU/memory allocation fails with an `EXCEEDED_CPU`-class error in logs; this is the practical gotcha for large/heavy newsletters (e.g. big attachments, heavy parsing) rather than Email Routing itself imposing a cost. — [Email Routing Limits](https://developers.cloudflare.com/email-routing/limits/)
- No explicit inbound rate limit is documented for Email Routing itself (only the size/rule/address caps below); rate limiting in practice would come from the Workers plan's request/CPU-time allowances.
- Routing rule/address caps (relevant since they bound the addressing scheme, see §2): **200 routing rules per zone/domain**, **200 verified destination addresses per account** (shared across all domains on the account); both are raisable via a Cloudflare limit-increase request form. — [Email Routing Limits](https://developers.cloudflare.com/email-routing/limits/), [Cloudflare Community thread confirming per-domain scope](https://community.cloudflare.com/t/do-200-rule-address-limits-apply-per-domain-or-total-all-domains/635943)

## 2. Per-user inbound address scheme

### Key Takeaways

- **Catch-all-to-Worker exists and is the clean solution here**: Email Routing supports a single catch-all rule per domain whose Action can be set to "Send to a Worker" — this forwards *every* address at the domain (including addresses that don't match any explicit rule, and misspelled/unknown local parts) to one Worker. This means Ownix does **not** need one routing rule per user; a catch-all rule alone routes all `*@leondev.xyz` (or a dedicated inbound subdomain) traffic to a single Worker, and the Worker reads the actual dialed address off `message.to` to determine which user it belongs to. — [Email Workers](https://developers.cloudflare.com/email-routing/email-workers/), [llms-full.txt](https://developers.cloudflare.com/email-routing/llms-full.txt)
- The catch-all rule still counts as one of the 200 rules per zone, but since it's a single rule regardless of user count, the 200-rule cap is irrelevant to a catch-all-based per-user scheme (it would only matter if using one explicit rule per user). — [Email Routing Limits](https://developers.cloudflare.com/email-routing/limits/)
- **Plus-addressing (RFC 5233 "subaddressing") is supported but is collapsed, not routed on**: Cloudflare's docs state that with subaddressing, `user+detail@example.com` is captured by the `user@example.com` custom address/rule — i.e., **the `+detail` portion is stripped for rule-matching purposes and does not create or select a separate destination**. If a routing rule/address for the exact literal `user+detail@example.com` already exists, that exact-match rule takes precedence over the bare `user@example.com` rule. Practically: plus-addressing is not usable to fan out per-user routing via distinct *rules* — it only affects which rule matches, and the detail portion has to be recovered by the Worker/application layer, not by Cloudflare's rule engine. — [llms-full.txt §Email Routing](https://developers.cloudflare.com/email-routing/llms-full.txt), spec origin: [RFC 5233 — Sieve Email Filtering: Subaddress Extension](https://www.rfc-editor.org/rfc/rfc5233.html) (defines the general "user+detail" / "user--detail" separator convention that Cloudflare's subaddressing feature implements)
- **Recommended pattern for Ownix**: a distinct local-part per user (e.g. `u_<token>@leondev.xyz`) routed through a single catch-all rule to one Worker, which reads `message.to` (the exact envelope RCPT TO, verbatim) to resolve the per-user token — this needs zero Cloudflare-side rule management per user and sidesteps the plus-addressing collapse behavior entirely. This also avoids the 200-address destination cap, since catch-all-to-Worker does not require each address to be a "verified destination address" (that cap applies to individually forwarded human mailboxes, not Worker-routed addresses).

## 3. Forwarded-mail authenticity / spoofing

### Key Takeaways

- Cloudflare's own postmaster docs state Email Routing **requires inbound mail to pass some authentication before it will accept/forward it at all**: "the email must either pass SPF or be correctly signed with DKIM," and DMARC is enforced at the MX (mail failing the sender domain's own DMARC policy is rejected outright, before ever reaching a Worker). — [Postmaster — Cloudflare Email Service docs](https://developers.cloudflare.com/email-routing/postmaster/)
- **However, that authentication verdict is not reliably exposed to the Worker.** A documented, currently-open Cloudflare `workerd` issue reports that Worker-delivered messages have **no `Authentication-Results` header at all**, and the `ARC-Authentication-Results` header that is present contains only `arc=none` with no actual `spf=`/`dkim=`/`dmarc=` verdict fields. The headers actually observed on the delivered message included: `arc-authentication-results` (verdict-less), `content-type`, `date`, `from`, `in-reply-to`, `message-id`, `mime-version`, `references`, `reply-to`, `subject`, `to`, `x-cf-spamh-score`, `x-gm-features` — i.e. a spam score header is present but no clean auth-pass/fail signal. — [cloudflare/workerd issue #6740](https://github.com/cloudflare/workerd/issues/6740)
- Practical implication for Ownix: **do not build spoofing defense on parsing `message.headers` for SPF/DKIM/DMARC verdicts** — that data either isn't present or isn't decodable today. The Cloudflare-side guarantee that actually matters is upstream of the Worker: Cloudflare's MX already rejected anything failing the sender's DMARC policy, so *by the time the Worker runs, the sender domain has already passed its own DMARC check* — that's a coarse "this came from somewhere claiming to be a real, DMARC-compliant domain" signal, not "this came from Cloudflare for *this* zone."
- The real trust boundary to build the webhook around is **Worker → FastAPI**, not **sender → Cloudflare**: since only Ownix's own Worker code can call the webhook, the practical minimum verification is a shared secret the Worker attaches to its `fetch()` call (e.g. a bearer token or HMAC signature over the POST body, configured as a Worker secret via `wrangler secret put`), which the FastAPI webhook validates before trusting `from`/`to`/body at all. This is the same pattern the project already uses for its Telegram webhook (per repo `CLAUDE.md`, `src/telegram/webhook.py`) — a shared-secret-validated inbound webhook — so no new authentication *primitive* is required, just wiring the Worker to send (and the backend to check) the secret.
- Separately, the per-user `to` address itself (§2) is a second, cheap authenticity gate: even if a spoofed message reaches the Worker, it can only target a `u_<token>@leondev.xyz` address if the attacker already knows a live, unguessable per-user token — so a random/opaque token (not a guessable username) narrows the actual attack surface to "attacker knows a specific user's private inbound address," not "attacker can inject arbitrary jobs for arbitrary users."

## 4. ESP tracking-link conventions

### Key Takeaways

- **Substack**: wraps every link in the HTML email version in a per-recipient Substack redirect domain (so the visible/hover URL is a Substack URL, not the original), and Substack provides **no publisher setting to disable this link-wrapping** in email. Substack also embeds a standard 1×1 open-tracking pixel (delivered via Mailgun infrastructure) in every email. — [Substack: "this email is being tracked"](https://alexhern.substack.com/p/this-email-is-being-tracked), [Substack custom domain support docs](https://support.substack.com/hc/en-us/articles/360051222571-How-do-I-set-up-my-custom-domain-on-Substack) (these are Substack's own writer/publisher and support surfaces, i.e. semi-primary; no dedicated Substack developer doc on the exact redirect URL grammar was found)
- **Mailchimp**: click-tracking redirects use the `*.list-manage.com` domain family (e.g. `https://exampledotcom.us4.list-manage.com/track/click?u=...&id=...&e=...`), a plain server-side HTTP redirect (no JS/rendering required to resolve). Click tracking is **on by default** for every campaign; senders can disable it in campaign settings, but Mailchimp still rewrites/redirects some links "to protect against malicious links" regardless, per free-plan behavior. Mailchimp confirms links are rewritten in **both HTML and plain-text** versions of a campaign — the plain-text version just shows the tracking URL as visible text instead of hiding it behind a hyperlink label. — [Mailchimp: Use Click Tracking in Emails](https://mailchimp.com/help/enable-and-view-click-tracking/), [Mailchimp: Troubleshooting Click Tracking](https://mailchimp.com/help/troubleshooting-click-tracking/)
- **Beehiiv**: default (non-custom-domain) tracking redirects run through `link.mail.beehiiv.com/ls/click?...`; publications with a "branded link" custom domain get `link.<their-domain>/ls/click?...` instead — same `/ls/click` path convention either way, standard HTTP redirect. — [beehiiv: Custom domains and branded links FAQ](https://www.beehiiv.com/support/article/35633518133783-custom-domains-and-branded-links-faq), [beehiiv: Understanding domains in beehiiv](https://www.beehiiv.com/support/article/12999491162391-understanding-domains-in-beehiiv)
- **ConvertKit / Kit**: click-tracking redirect domain is `click.convertkit-mail.com`; open-tracking pixel is served from `open.convertkit-mail.com`. The `convertkit-mail.com` infrastructure/domain names did not change after the ConvertKit→Kit rebrand. (Sourced from third-party analysis, not a ConvertKit/Kit developer doc — treat the exact domain as likely-correct but not contractually guaranteed to stay stable.)
- **Resolution approach**: all four ESPs above use plain HTTP 30x redirects, resolvable with a normal `GET`/`HEAD` request following the `Location` header chain (no JS execution/headless browser needed) — this matches the `/ls/click`, `/track/click`, and Substack-domain patterns all being server-side redirect endpoints, not JS-rendered landing pages.
- **RFC framing for multipart handling** (relevant to which body Ownix should parse first): RFC 2046 specifies that in a `multipart/alternative` MIME entity, parts must be ordered least-to-most preferred and a receiving agent should render/use the **last** part it can handle — in practice this means the `text/html` part (when present) is the "preferred" representation the sender intends, and is also where ESP link-wrapping actually lives; the `text/plain` alternative may contain either the same wrapped tracking URLs as visible text (Mailchimp) or no links at all. — [RFC 2046 §5.1.4](https://www.rfc-editor.org/rfc/rfc2046.html)

## 5. Common pitfalls in "forward a newsletter into a read-it-later/curation tool"

### Key Takeaways

- **HTML vs. plain-text divergence is real and ESP-dependent**: Mailchimp's own docs confirm plain-text versions of a campaign are **not** guaranteed link-free — they show the same tracking URLs as raw visible text — but other ESPs' plain-text alternative parts may omit links Ownix actually wants (e.g. a plain-text part that only says "view in browser: <url>"). A robust parser needs to prefer the `text/html` MIME part when present (per RFC 2046 above) and fall back to `text/plain` only when no HTML part exists, rather than assuming plain-text is a safe simplification. — [Mailchimp: Use Click Tracking in Emails](https://mailchimp.com/help/enable-and-view-click-tracking/)
- **Tracking pixels look like content but aren't**: every major ESP researched (Substack via Mailgun, Mailchimp, Beehiiv, ConvertKit) embeds a 1×1 (or similar) invisible image for open-tracking. A naive "extract all `<img>`/all URLs" pass will pick these up; they need to be filtered out (e.g., by image dimension/`display:none` heuristics, or simply by never treating `<img>` src values as candidate "article links" — only `<a href>` values should be considered content-link candidates).
- **"View online"/"read in browser" links are a distinct, easily-confused category**: this is the single biggest documented pitfall pattern across ESPs — a newsletter can legitimately put its actual content behind one dominant "view this post" / "read online" link (observed as a named pattern on Substack specifically, where some publishers rely on the web version for anything beyond a short teaser) with **no other inline content links in the email body at all**. A naive extractor that just grabs "the first link" or "all links" either mistakes the view-online link for content, or extracts zero article links when that's actually the *only* link worth following. The pipeline needs an explicit rule to recognize and either follow-through or specially flag single-link "read online only" newsletters, since for Ownix's job-creation logic this is a materially different case (one URL = "the newsletter itself," to be unwrapped and treated as the single item) versus a normal multi-link digest (many URLs = many candidate jobs).
- **Unsubscribe/manage-preferences links are boilerplate noise, not content**: every ESP footer includes an unsubscribe/manage-subscription link (and Beehiiv/Mailchimp/ConvertKit all also inject a "web version"/"view in browser" link near the top) — both categories sit in the same `<a href>` pool as real content links and need positional/domain heuristics (e.g. footer proximity, or matching against each ESP's known unsubscribe-path conventions) to exclude, rather than relying on link text alone (translations/customized anchor text can't be assumed).
- **Redirect-chain resolution is required, not optional, before dedup/storage**: since Mailchimp/Beehiiv/ConvertKit all wrap outbound links in per-recipient/per-campaign tracking redirects (§4), storing the raw `href` values as "the article URL" would (a) store ESP tracking domains instead of the real destination, and (b) break Ownix's existing job dedup logic (which presumably dedupes by URL) since the same article would get a different tracking URL in every single newsletter send/recipient. The parser must follow each redirect chain to its final destination **before** calling `create_and_enqueue_job()`, and should cap chain length / set a timeout given some ESP redirects can nest (e.g. a link-shortener in front of an ESP tracking domain in front of the real article).
- **General tooling precedent for fragility**: Zapier's own Email Parser docs/community note that its template-based email parsing "breaks when a sender reformats their email" and has no resilience to layout drift — a cautionary precedent that Ownix's HTML-structure-based link extraction (rather than fixed field templates) is the more robust design choice, but still implies per-ESP layout changes are an ongoing maintenance surface, not a one-time build. — [Zapier: Email Parser guide](https://zapier.com/blog/email-parser-guide/), [Zapier Community: HTML table parsing thread](https://community.zapier.com/how-do-i-3/best-approach-to-parse-an-html-table-in-email-45966)
- **Feedbin's model confirms per-user-address + group-by-sender is the standard shape** for this exact feature (forward newsletter → per-user unique address → ingest as a feed grouped by originating sender): Feedbin issues each account a unique "secret" forwarding address and groups incoming newsletters into separate feeds by sender — directly analogous to Ownix's planned per-user alias → auto-created Space design. Feedbin's own material doesn't document deeper HTML/plain-text or tracking-pixel handling specifics (that layer isn't publicly documented by Feedbin), so no additional primary detail was available there beyond the addressing/grouping shape. — [Feedbin blog: Subscribe to Email Newsletters in Feedbin](https://feedbin.com/blog/2016/02/03/subscribe-to-email-newsletters-in-feedbin/)
- Readwise Reader's public email-ingestion page returned HTTP 404 at research time (`https://readwise.io/reader_email`), so no primary-source detail from Readwise could be confirmed for this file — flag as unresolved if Readwise's exact behavior becomes relevant later (worth re-checking the current URL directly rather than relying on this note).
